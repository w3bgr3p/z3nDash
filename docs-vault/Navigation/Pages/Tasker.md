# Tasker

Tasker — страница `/tasker.html` для хранения расписаний и запуска локальных задач.

## Список

Задачи читаются из таблицы `schedules`. В списке отображаются имя, состояние и основные параметры запуска.

## Редактирование

Для задачи задаются:

- имя;
- executor;
- путь к скрипту, файлу или задаче;
- аргументы;
- состояние `enabled`;
- расписание;
- политика overlap;
- payload.

Поддерживаемые executor:

| Executor | Что запускает |
|---|---|
| `python`, `node`, `ts-node`, `npm` | скрипты соответствующих сред |
| `exe`, `cmd`, `bat`, `bash`, `ps1` | исполняемые файлы и командные сценарии |
| `csx` | C#-скрипт; в списке задач для него есть кнопка проверки компиляции |
| `xml` | шаблон ZennoPoster: граф из XML проигрывает встроенный рантайм, браузер выбирается в карточке задачи |

Несколько задач можно выделить через `Ctrl+клик`; `Shift+клик` выбирает диапазон.
Изменённые поля вкладок **Settings** и **Schedule** сохраняются во все выбранные
задачи, при этом имена не копируются. Клавиша `Delete` удаляет выбранную задачу
или весь набор после подтверждения.

## Ресурсы

RAM и CPU показаны для каждой задачи и суммарно в заголовке. На Windows в расход
экземпляра входят дочерние процессы, включая браузеры. CPU — доля всей машины,
доступная после второго измерения. Память самого z3nDash показана отдельно;
XML-прогоны внутри процесса отмечены без выдуманного индивидуального расхода.

## Расписание

UI умеет формировать:

- запуск по требованию;
- ежедневный запуск;
- запуск по дням недели;
- запуск по дню месяца;
- интервал в минутах.

Итоговые значения сохраняются в `cron`, `interval_minutes` и `fixed_time`.

## Overlap

- `skip` — не запускать новый экземпляр, пока активен предыдущий;
- `parallel` — разрешить несколько экземпляров до `max_threads`;
- `kill_restart` — остановить активные экземпляры и запустить новый.

## Аккаунт под прогон шаблона

Экзекутор `xml` резервирует аккаунт, только если шаблон действительно с ним работает: переменная `acc0` объявлена в блоке `<Variables>` **и** упомянута где-то ещё — в шаге или в собственном коде. Одного объявления мало: в шаблоны ZennoPoster переменные переезжают из проекта-донора пачкой и часто никем не читаются.

Резервирование включается также, если в payload задачи явно задан `accountTable` или `condition`. И не включается, если в payload уже пришёл непустой `acc0` — значит, аккаунт выбран вручную.

Таблица берётся из `payload.accountTable`, иначе это `__<имя задачи до первой точки>`. Условие — `payload.condition` (подстрока `NOW` заменяется на текущее время UTC), по умолчанию `1=1`.

Взятый аккаунт получает `status = 'busy'`, а его колонки, строка из `instance` и из `folder_profile` попадают в переменные проекта и в payload запуска — оттуда ветка `xml` берёт прокси и профиль браузера, поэтому данные аккаунта перекрывают значения из настроек задачи.

Освобождение идёт в `finally`: `idle` на успехе, `fail` на любом другом выходе, включая снятие по лимиту времени. Падение самого освобождения пишется предупреждением и прогон не роняет.

Отдельные случаи:

- таблицы аккаунтов нет — это ошибка настройки: статус `error`, `last_exit = -1`;
- свободных аккаунтов по условию нет — прогон не состоялся: `last_exit` пустой, счётчики `runs_total` и `runs_success` не трогаются.

## Лимит времени прогона

Поле **Max runtime** в настройках задачи (колонка `timeout_seconds`). `0` — лимита нет.

По истечении лимита прогон обрывается, в вывод пишется строка о лимите, прогон засчитывается как неудачный (`last_exit = -1`).

Как именно обрывается — зависит от экзекутора:

- внешний процесс (`python`, `node`, `cmd`, `npm`, …) снимается вместе с деревом дочерних процессов — остановка по факту;
- `xml` получает отмену `CancellationToken`. Отмена кооперативная: токен проверяется между ветками, а код, который токен не смотрит, ею не прервётся.

## Управление

Доступны:

- Run;
- Stop;
- Restart;
- включение/отключение расписания;
- удаление и дублирование;
- открытие файла и каталога;
- открытие терминала;
- проверка/установка зависимостей Python и Node.

Run, пауза/включение расписания, Resume schedule, Restart, Interrupt и Eliminate
применяются ко всем выбранным задачам. Run ставит указанное число прогонов каждой
задачи в очередь; заголовок показывает размер выделения. Групповая команда
продолжается после отдельных ошибок и собирает их в одно сообщение. Interrupt
может также очистить ожидающие прогоны.

`POST /tasker/run` принимает необязательную непустую строку `args` для ручного
залпа: она заменяет сохранённые аргументы в очереди, не меняя задачу. Флаги payload
добавляются как обычно. Подробности — [[Task API]].

## Output

Вывод активного запуска передаётся через SSE. Для нескольких параллельных экземпляров доступны отдельные `runId`.

## Traffic

Вкладка задачи с трафиком из `trafficLog.jsonl`:
`GET /traffic?tail=N&task_id=...`, опрос раз в 3 секунды. Пишет его ZpRuntime,
подробности — в [[Traffic]]. Файл ротируется сам.

## Payload

Payload состоит из schema и values. Его можно редактировать, импортировать, экспортировать и передавать executor при запуске.

У поля есть тип, заголовок, флаг аргумента, позиция, значение по умолчанию и enum;
порядок меняется перетаскиванием. Предпросмотр команды показывает аргументы из
значений. Схему можно заполнить по Python `argparse` и `click`: скрипт разбирается,
но не запускается.

**Skip empty** пропускает пустое значение, чтобы скрипт использовал своё значение
по умолчанию. Без него пустое значение передаётся явно. Пароли маскируются в
предпросмотре и строке `[launch]` лога. Ошибка преобразования аргументов
останавливает запуск на `step=payload`.

## API

Управление из работающего скрипта без поиска ID: [[Task API]].
Доступны отсрочка следующего запуска, пауза и возобновление расписания.

Основные маршруты:

- `GET /tasker/list`
- `POST /tasker/save`
- `POST /tasker/delete`
- `POST /tasker/run`
- `POST /tasker/stop`
- `GET /tasker/instances`
- `POST /tasker/kill-instance`
- `GET|POST /tasker/payload`
- `GET /tasker/output/stream`
- `GET /tasker/queue`
- `POST /tasker/clear-queue`
