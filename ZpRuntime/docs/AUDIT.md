# Карта подложки ZpRuntime и дневник проверки

Зачем этот файл. Перенесённый из z3n7 код сверяется диффом — там ошибку «тихо
делает не то» внести нельзя. А наша подложка под ним написана самостоятельно, и
именно в ней нашлись методы, которые **не падали, а молча делали не то или
ничего**: клик уходил синтетическим событием, ввод — одним присваиванием вместо
набора, часовой пояс не выставлялся вовсе. Наверх при этом шло «успешно».

Сборка такое не ловит. Прогон шаблона тоже: «ветка прошла» значит только «не
бросила исключение». Ловится это сверкой каждого метода с тем, что вызов
означает в ZennoPoster, — и вот её учёт.

## Статусы

| статус | значение |
|---|---|
| `копия` | дословная копия эталона, сверяется диффом, глазами не требует |
| `проверено` | сверено с семантикой ZP; в колонке «чем» сказано как именно |
| `отказ` | намеренно бросает `NotSupportedException` с внятным текстом |
| `не проверено` | написано нами и глазами не сверялось — здесь и живут тихие поломки |

Проверкой считается только то, что видно снаружи: поведение на живой странице,
трафик, состояние DOM. «Прочитал код и выглядит правильно» — это `не проверено`,
именно так и были пропущены `FillAsync` и `DispatchEvent`.

## Дневник

Записи снизу вверх, новые сверху.

### 2026-08-22 — «not found» про элемент, который был на экране

`not found in 30s: tag=[input:text] attribute=[id] pattern=[phone-or-email]` —
при том, что поле стояло на странице задолго до падения. Вывод был ложью, и это
худший вид поломки: ветка не сломалась, она уверенно сообщила неправду.

**Причина.** ZP пишет тип поля через двоеточие: `input:text`, `input:password`.
Перевод этой записи в CSS стоял ровно в **одной** ветке поиска — по
`fulltagname`:

```csharp
if (attr == "fulltagname")
{
    string cssTag = tag.Contains(':') ? $"{tag.Split(':')[0]}[type='{tag.Split(':')[1]}']" : tag;
```

Во всех остальных — точное совпадение, регулярка, поиск по тексту, поиск по
потомкам — тег уходил в селектор как есть. А это не CSS:

```
querySelectorAll("input:text[id='phone-or-email']")
  SyntaxError: 'input:text[id='phone-or-email']' is not a valid selector.
querySelectorAll("input[type='text'][id='phone-or-email']")
  нашёл 1
```

Цикл ожидания `HeSet`/`HeClick` ловит исключения и пробует снова, поэтому
ошибка разбора селектора наружу не выходила ни разу — накапливалась в
`lastExceptionMessage` и в конце выдавалась как «элемента нет». Поднятие
ожидания до 30 секунд, естественно, ничего не меняло: невалидный селектор
невалиден и через час.

**Исправлено** одним нормализатором `CssTag` (и `XPathTag` для XPath-пути),
применённым во всех местах, где тег превращается в селектор: точное совпадение,
`fulltagname`, поиск по тексту, XPath, поиск по потомкам — и в JS-движке
`RegexSelector`, где `querySelectorAll` бросал ровно ту же `SyntaxError` внутри
страницы.

**Чем проверено.** Страница с двумя text-полями, password-полем и кнопкой:

```
input:text + id (точное)        найден id=phone-or-email    84 мс
input:text + id (регулярка)     найден id=phone-or-email    30 мс
input:password + id             найден id=pw                 7 мс
input:text + fulltagname        найден id=phone-or-email     4 мс
button + innertext (регулярка)  найден id=go                24 мс
input + id (без типа)           найден id=other              3 мс
HeSet отработал за 5888 мс, в поле: +380501234567
```

Последняя строка — то, ради чего всё: ветка `SetAttribute` действительно вводит
текст в поле, которое раньше «не находилось».

**Урок про диагностику.** Симптом «not found» уводил в сторону ожидания: сначала
чинился срок, и правильно, но сама ошибка была не в нём. Цикл, который глотает
исключения ради повторов, обязан показывать, **чем** он занят — иначе разбор
селектора и отсутствие элемента выглядят одинаково. Здесь это стоило двух
прогонов чужого времени.

### 2026-08-22 — срок ожидания элемента брался из константы, а не из ветки

`not found in 10s` на ветке, где в шаблоне выставлено 30. Ожидание было зашито
числом:

```csharp
/// <summary>Сколько ждать элемент. В XML срока нет — берём ZP-шный по умолчанию.</summary>
private static int Deadline(Branch branch) => 10;
```

Комментарий неправда: срок в XML есть — `<WaitElementTime>` в секундах, поле ZP
«Время ожидания элемента». В шаблонах он у веток разный, встречается и 60.
Правка шаблона молча не доезжала: ветка падала на медленном сайте ровно тем же
текстом, что и на быстром.

**Проверено часами.** Ветка с заведомо отсутствующим элементом:

```
WaitElementTime=3    ждали   3101 мс, «not found in 3s»
WaitElementTime=8    ждали   8149 мс, «not found in 8s»
поля нет             ждали  10190 мс, «not found in 10s»
WaitElementTime=0    ждали      0 мс, «not found in 0s»
```

Ноль пропускается как есть: в ZP это «не ждать», подменять его десяткой значит
менять смысл ветки.

**Сверка всего, что лежит в ветках.** Раз одно поле читалось неправильно, стоило
пересчитать остальные — сопоставлены имена параметров из шаблонов с тем, что
плеер читает. Нашлось второе такое место:

```csharp
var level = branch.Param("EmulationLevel");
return string.IsNullOrWhiteSpace(level) || level == "Current" ? _instance.EmulationLevel : level;
```

Полей два: `<Emulation>` говорит, откуда брать уровень (`Current` — «как у
инстанса»), а `<EmulationLevel>` — сам уровень (`Middle`). Проверялось равенство
`Current` у второго, где лежит уровень, поэтому условие не срабатывало никогда.
Исправлено. **Статус — `не проверено`:** сегодня это ненаблюдаемо, потому что
`RiseEvent` уровень эмуляции игнорирует, клик всегда идёт настоящей мышью.
Записано, чтобы не выдавать правку по контракту за проверенную.

Остальное не читаемое из веток — осознанно: `Imposition`, `FilePath`, `Units`,
`ProccessingResult`, `ConnectionType` у `WaterMark` (см. запись про неё),
`ReturnType` у `OwnCode`, `Save*` у `Profile/Update` (ветка целиком пропускается),
`Variable` у `Logic/Switch` (ветка не реализована).

### 2026-08-22 — релей прокси: вниз HTTP, наверх SOCKS5

Chrome показывал плашку «You are using an unsupported command-line flag:
--host-resolver-rules=...». Ключ ставит не наш код, а драйвер Patchright, и
только для SOCKS5:

```js
const isSocks = proxyURL.protocol === "socks5:";
if (isSocks && !options.socksProxyPort)
  chromeArguments.push(`--host-resolver-rules="MAP * ~NOTFOUND , EXCLUDE …"`);
```

Ключ по делу: он валит локальное разрешение имён, чтобы Chrome отдал домен
прокси, а не резолвил его сам мимо. Но плашка занимает высоту окна — сдвигает
вьюпорт и попадает в скриншоты, а по ним считаются координаты кликов и
`DrawPartAsBitmap`. Просто убрать ключ нельзя: это утечка DNS.

**Сделано.** Релей теперь отдаёт браузеру `http://127.0.0.1:порт` вместо
`socks5://`. В HTTP-прокси браузер пишет имя хоста в `CONNECT` и сам ничего не
резолвит, поэтому ключ не нужен вовсе: имя доходит до нас и уходит наверх типом
адреса `0x03`. Утечки нет по устройству протокола, а не по ключу.

Вниз поддержаны оба вида запроса: `CONNECT host:port` (весь HTTPS, дальше труба
байт в байт) и абсолютная форма `GET http://host/path` — она переписывается в
обычную и помечается `Connection: close`, иначе браузер послал бы следующий
запрос, возможно к другому хосту, в уже открытую наверх трубу.

**Найдено попутно, и это была настоящая поломка.** Согласование способа входа
предлагало прокси **только** «логин с паролем»:

```csharp
await up.WriteAsync(new byte[] { 0x05, 0x01, 0x02 });
if (choice[1] != 0x02) return false;
```

Прокси, отвечающий `0x00` «вход не нужен», получал от нас разрыв. Теперь
предлагаются оба способа, выбирает сервер.

**Молчание убрано.** Все отказы уходили в пустой `catch`, и наружу это выглядело
одинаково — `ERR_EMPTY_RESPONSE` без причины. У релея появился `Log`, а
`LaunchAsync` принимает его и прокидывает: планировщик пишет в отчёт задачи,
`XmlInspect` — в консоль. Именно этот лог и показал причину за один прогон.

**Чем проверено.** Сначала — на живом стороннем прокси. Тот, что записан в
`simroute_test.xml`, для этого не годится: он отклоняет учётки сам, и это видно
независимо от нашего кода —

```
curl --socks5-hostname … -U …
* User was rejected by the SOCKS5 server (5 2).
```

Рабочий нашёлся в базе проекта (колонки `proxy` в `_instance`, `profile`, `api`).
Там 1212 записей, все в виде `http://` — для них Chromium авторизуется сам, релей
не включается и ключа не бывает вовсе. Из выборки в 14 хостов живым оказался
один, и он же отвечает по SOCKS5 на том же порту. На нём:

```
релей отдаёт: http://127.0.0.1:5821
  HTTPS: {"ip":"82.23.203.206"}   HTTP: {"ip":"82.23.203.206"}
host-resolver-rules: False
proxy-server=http://127.0.0.1:5830
браузер вышел как: {"ip":"82.23.203.206"}
```

То есть весь путь целиком: браузер → наш HTTP-релей → чужой SOCKS5 с логином →
интернет, и адрес выхода — прокси, а не наш.

Отдельно, чтобы проверить то, чего чужой прокси не показывает — какой тип адреса
до него доехал, — поднят свой SOCKS5 с обязательной авторизацией, который это
записывает. Через `HttpClient`:

```
HTTPS — {"ip":"187.190.175.41"}, HTTP — то же
до прокси дошло: имя:api.ipify.org (оба раза), отказов по логину 0
```

И с настоящим браузером:

```
host-resolver-rules в командной строке: False
proxy-server=http://127.0.0.1:6822
страница: {"ip":"187.190.175.41"}
до прокси дошло: имя:clients2.google.com, имя:safebrowsingohttpgateway.googleapis.com,
                 имя:www.google.com, имя:accounts.google.com, имя:api.ipify.org
адресами, а не именами: 0
```

Ноль обращений адресом — это и есть доказательство, что DNS не утекает: ни один
запрос браузера не был разрешён локально. Пароль в проверке взят с `:` и `@`
внутри, чтобы заодно проверить разбор строки прокси.

### 2026-08-22 — переход падал на загруженной странице

Прогон шаблона: `[ERR] прервано на ветке OwnCode/CSharp: Timeout 30000ms
exceeded, navigating to "https://www.airbnb.fr/", waiting until "load"`. Страница
при этом была загружена, и в ZP исключения в этом месте нет.

**Причина.** Наш `Navigate` звал `GotoAsync` с настройками по умолчанию: ждать
состояния `load`, на таймауте бросать. У ZP переход так не устроен, и эталонный
`Go` это прямо показывает:

```csharp
if (go) instance.ActiveTab.Navigate(url, "");
if (instance.ActiveTab.IsBusy && waitTdle) instance.ActiveTab.WaitDownloading();
```

Ждать или не ждать решает вызывающий, а не переход. Мы же ждали всегда — и на
сайте, где аналитика не даёт `load` случиться, роняли ветку на готовой странице.

Тем же болел `WaitDownloading`: `WaitForLoadStateAsync` на таймауте бросает, а
«подожди загрузку» — это ожидание, а не проверка.

**Исправлено.** `Navigate` возвращается на `WaitUntilState.Commit` — как только
новый документ принят. `WaitDownloading` по истечении срока просто возвращается
(ловим `PlaywrightException`: у Playwright свой `TimeoutException`, и он от неё
наследуется, заодно ловится смена документа во время ожидания).

**Чем проверено.** Тот же airbnb.fr:

```
Go вернулся за 661 мс, без исключения
IsBusy сразу после — True, то есть ветка «ждать» у Go рабочая
WaitDownloading вернулся за 913 мс; readyState complete, body 474102 символа
```

Отдельно проверен сам таймаут — страница с картинкой на маршрутизируемый в
никуда адрес, где `load` не наступает:

```
Navigate вернулся за 35 мс, без исключения; IsBusy True, текст страницы читается
WaitDownloading вернулся за 21087 мс, без исключения
```

**Чего это стоит.** `Navigate` больше не гарантирует загруженную страницу — как
и в ZP. Код, который на это молча рассчитывал, теперь обязан спросить `IsBusy`
или позвать `WaitDownloading`. В шаблонах переход идёт через `Go`, а он это уже
делает.

### 2026-08-22 — перенос `Browser/Cookies.cs`: срок жизни уезжал молча

Перенесены `Browser/Cookies.cs` и `Browser/CookieCollector.cs` — дословно.
Перенос был заблокирован подложкой: `Instance.GetCookie` бросал
`NotSupportedException`, а его зовут `Cookies.GetCookies`, `SaveAllCookies` и
`SaveDomainCookies`, то есть вся выгрузка сессии. Реализован через
`_context.CookiesAsync()`.

**Найдено при проверке, а не при чтении.** Первая версия писала колонку
`expires` в unix-секундах — так её пишут выгрузки расширений, и так её читал наш
же разбор. Эталонный `Cookies.NetscapeToJson` разбирает её
`TryParseExact("MM/dd/yyyy HH:mm:ss")` и на несовпадении **не бросает**, а кладёт
`expirationDate = null` и `session = false`. То есть `GetCookies()` отдавал
формально правильный JSON, в котором у каждой cookie пропал срок: сохранённая
сессия превращалась в сессионную и умирала с браузером.

Второй заход, уже с маской, но в UTC, дал ту же болезнь мягче: срок уезжал ровно
на смещение пояса, у меня +5 часов. Причина — `NetscapeToJson` заворачивает
разобранное в `new DateTimeOffset(expiry)`, то есть считает время **местным**.
Пишем местное.

Правки в `PlaywrightInstance`: `FormatNetscapeExpiry`/`ParseNetscapeExpiry`,
девять колонок вместо семи (добавились `httpOnly` и хвостовой `FALSE` — их
пишет `JsonToNetscape` эталона), и обратный разбор в `SetCookie` перестал
терять срок и `httpOnly`.

**Чем проверено.** Живой браузер, `example.com`, две cookie с `max-age=86400`:

```

  example.com | FALSE | / | FALSE | 08/23/2026 10:40:48 | probe | 42 | FALSE | FALSE
GetCookie("example.com")   — те же две
GetCookie("nonexistent.tld") — []
GetCookie(isCookieFormat)  — probe=42; second=abc
Cookies.GetCookies(json)   — expirationDate 1787499648, совпадает с настоящим
ClearCookie → []           → SetCookie(netscape) → document.cookie = probe=42; second=abc
GetCookie после round-trip — срок тот же
```

Отдельно проверены `GetCookiesByJs` (вернул cookie живой страницы),
`SetCookiesByJs` (`viajs=777` появилась в `document.cookie`), `ParseJwt`
(разобрал заголовок, `sub`, `iat`) и `CookieCollector.Run` — сходил в сеть за
`example.com` и `wikipedia.org`, принёс 5 настоящих cookie.

**Баг эталона, чинить в z3n7.** `ConvertCookieFormat(json, "netscape")` уводит
срок на смещение пояса: `NetscapeToJson` читает колонку как местное время, а
парный `JsonToNetscape` пишет её из UTC. Круговой прогон json→netscape→json
сдвигает срок на величину пояса, у меня на 5 часов. В копии не тронуто.

**Не проверено, упирается в базу.** `AnalyzeCookies`, `PruneCookies`,

`LoadCookies`, `CleanDomainInDb` ходят в `DbGet`/`DbUpd`. Проверка упирается в
известный баг эталона: в режиме SQLite запись уходит в никуда (см. запись ниже).

### ВАЖНО: в режиме SQLite запись уходит в никуда

Это баг **эталона**, перенесённый дословно, и чинить его надо в z3n7. Но знать о
нём нужно сейчас, потому что он тихий и полный.

`DbCore.DbQ` открывает соединение так:

```csharp
using (var db = dbMode == "pgSQL" ? new Sql(dbSource) : new Sql(sqLitePath, null))
```

Путь к файлу берётся из **параметра** `sqLitePath`, а не из `dbSource`. Параметр
по умолчанию `null`, и весь перенесённый слой — `DbGet`, `DbUpd`, `SqlGet`,
`DbInsert` — зовёт `DbQ` без него. В результате каждый вызов открывает пустую
безымянную базу, которая умирает вместе с соединением.

Проверено прямо:

```
dbSource = …/devdeck-dbsource-check.sqlite
CREATE TABLE probe → ошибки нет
INSERT           → ошибки нет
SELECT id FROM probe → [] и «no such table: probe»
файл существует: False          ← база так и не создана

тот же запрос с явным sqLitePath → [7], файл создан, размер 8192
probe виден в реальной базе: 0   ← созданного там нет
```

То есть на SQLite запись молча уходит в никуда, а чтение сообщает «нет такой
таблицы». В pgSQL всё в порядке: там строка подключения берётся из `dbSource`.

Само по себе это не падает — и потому опаснее всего: находится не тот элемент, а
вместе с лишними совпадениями сдвигается `Number`, по которому ветка выбирает
нужный. Клик уходит не туда молча.

Насколько это важно, видно по самим шаблонам: `regexp` — не редкий случай, а
половина поисков в `simroute_test` (6 из 12) и две трети в `numlex` (23 из 34),
причём в основном по `class`.

Теперь регулярка выполняется там, где ей и место — в самой странице. Playwright
позволяет зарегистрировать свой движок селекторов; он живёт наравне с `css` и
`xpath`, поэтому `Locator` остаётся ленивым и переживает перерисовку DOM
(`RegexSelector.cs`).

Проверено на четырёх `div` с классами `btn-a`, `btn-b`, `btn-c`, `xbtn-a`:

```

^btn-         → 3: A,B,C    (приближение дало бы 4)
btn-c$        → 1: C
```

### 2026-08-13 — загрузка страницы, мышь, клик, ввод

**`IsBusy` всегда возвращал `false`** — и это ломало не наш код, а перенесённый.
В `InstanceExtencions.Go` и `F5` написано
`if (ActiveTab.IsBusy && waitTdle) ActiveTab.WaitDownloading()`, то есть ожидание
загрузки **не выполнялось никогда**. То же условие стоит в `Canvas.cs` перед
каждым скриншотом. Теперь читается `document.readyState`.

Ограничение, которое надо знать: `readyState` относится к текущему документу, а
между началом перехода и его фиксацией старый документ ещё `complete`. Окно
между «браузер пошёл по адресу» и «новый документ начался» этим способом не
ловится. Для честного покрытия нужен CDP `Page.frameStartedLoading` с состоянием
на страницу — пока не сделано.

**`FullEmulationMouseMove` телепортировал курсор.** Один `MoveAsync` без `Steps`
ставит мышь в цель, не побывав между. Метод называется `FullEmulation`, и
вызывающий код на эту эмуляцию рассчитывает. Теперь число шагов от расстояния.

**Заодно внешне подтверждены правки 8c03be8**, которые до сих пор были проверены
только чтением: клик приходит с `isTrusted: true`, ввод идёт посимвольно.

**Чем проверено.** Обработчики событий на самой странице — они видят ровно то же,
что увидел бы антибот.

```
readyState complete → IsBusy: False
readyState loading  → IsBusy: True
после close()       → IsBusy: False
событий mousemove за один FullEmulationMouseMove: 41
click.isTrusted: true
keydown на ввод 5 символов: 6
значение поля: abcde
```

Первый заход на `IsBusy` был негодным: я навигировал через `Navigate`, а он сам
дожидается загрузки, поэтому «во время загрузки» проверялась уже загруженная
страница и тест показывал `False` на обеих строках. Заменено на `document.open()`
/ `close()` — состояние задаётся детерминированно.

**Найдено, но не исправлено:** `Tab.Handle` отдаёт `GetHashCode` вместо HWND. Как
ключ годится, для `Emulator.SendKey` — нет. Зовёт его `ChromeExt.cs`, который ещё
не перенесён, так что сейчас это мина, а не поломка.

### 2026-08-13 — cookie: круговой прогон

Проверял `SaveCookie` → `ClearCookie` → `SetCookie` на живом браузере
(Patchright, headless, example.com), а не чтением кода.

**Найдено, подтверждено, исправлено.** `SaveCookie` писал строку вида
`name=value; name=value`. Она не читалась ничем из того, что её ждёт:

- `Rqst.GetCookiesForRequest` разбирает переменную `cookies` как `JArray` и
  берёт `cookie["domain"]` — на такой строке разбор падал в `catch` и метод
  возвращал `null`, то есть запрос уходил **без cookie и без единого сообщения**;
- `Cookies.ConvertCookieFormat` на ней бросает «Unknown input format».

Вместе с форматом терялись домен, путь, срок и `httpOnly`. При этом
`SaveCookies()` отрабатывал «успешно» — ровно тот случай, ради которого этот
дневник и заведён.

Теперь выгружается JSON-массив с теми полями, которые читает эталон. `SetCookie`
сведён в один метод рядом с выгрузкой и понимает три формата: JSON, Netscape
(его разбор лежал отдельно в `CanvasExtensions.cs`) и `name=value` — у последнего
домен берётся из текущей вкладки, потому что в самой строке его нет.

**Чем проверено.** Выставил cookie на странице, выгрузил, убедился что
`JArray.Parse` проходит и поля на месте, очистил, загрузил обратно, перешёл на
страницу — `document.cookie` вернул `probe=42`.

```
probe: domain=example.com path=/ value=42 exp=1786668160
после очистки:
после SetCookie: probe=42
```

Попутно этим же прогоном подтвердились: `Go` (переход состоялся),
`EvaluateScript` в форме с `return`, `ClearCookie`.
